## 3. 新发现缺陷

### N1 · 断线补发被服务端监听器注册竞态吞掉（中危，功能未达成）

**现象**：停服后翻页（pending 正确缓存），重启服务，WS 重连成功（绿点亮），但服务端状态永远停在断线前位置。补发在每次重连中都不会生效。

**根因**（受控实验确证）：客户端补发时机是 `open` 事件内同步 `send`（useBookdSocket.ts:25-31）；而服务端 `connection` 回调是 async 的（server.ts:62-72）——`hello` 的参数含 `await library.listBooks()`，**在该 await 挂起期间 `message` 监听器尚未注册**。EventEmitter 对无监听器的事件直接丢弃，不缓冲。本地环回的补发消息必然先于 listBooks 完成而到达 → 必丢。

**实验证据**：新建 WS 连接，open 后立即发 `progress: 0.61`、另一连接延迟 300ms 发 `progress: 0.62`——服务端只收到 0.62，0.61 无痕丢失。竞态窗口真实存在且大于本地消息往返。

**责任划分**：实施方案 §2.5 明文规定"在 open 监听器里补发"，坑在方案里，执行如实照做——**方案责任，非实施错误**。

**修复建议（两层）**：

1. **客户端最小修**（不破服务端红线，推荐立即做）：补发从 `open` 回调移到 `hello` 消息处理分支——hello 到达即证明服务端 connection 回调已执行到 send 之后，message 监听器在同一同步 tick 内注册完毕，往返延迟远大于该 tick，安全。副产品：顺序变为"先收旧态、再补发新态、服务端广播纠正"，方案 §2.5 已知的"旧状态回闪"一并消除。
2. **服务端根治**（列入 backlog，与上次审计 H 类一起做）：`connection` 回调先注册 `on('message')` 再 await/发送 hello（server.ts:62-72 内一次顺序调整）。这是既有设计脆弱点——任何"连上就说话"的客户端都会踩，本次只是第一个踩中者。

**修复后验收**：重复本报告的停服实验——停服 → 翻 N 页 → 重启 → `curl /api/state` 应反映断线期间最新位置；并补一条集成测试（server.test.ts 已有 WS 往返测试设施，加"连接后立即发 state:update 不丢"用例，该用例同时锁死服务端根治不回退）。

## 4. 次要观察（不阻塞，按需处理）

- **O1 · 选区 10 秒自动清除**（App.tsx:116-120，既有行为）：用户在笔记框打字超 10s，选区连同卡片被清，笔记被打断。建议：selection 存续期间若笔记框有焦点或非空则不清。

- **O3 · 设置面板打开时方向键仍翻页**：轻微焦点语义问题。
- **O4 · 初始视口瞬态窄会让两栏开局收起**（既有行为）：`leftOpen` 初值一次性求值 `matchMedia`，窗口从窄变宽不自动展开。现在有了重开浮钮，危害已从"死路"降为"多一次点击"。
- **O5 · 正面**：`--theme-bg-color` 注入是查过 foliate 上游的正确做法（paginator.js:675 消费，填充页缘背景）；散落硬编码纸面色全量迁移 CSS 变量属"好的超范围"——不迁移则纸面切换必有残色，实测无回归。此类超范围今后应在 PROGRESS 中主动声明。
