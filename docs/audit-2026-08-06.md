方法：两轮独立审计——(1) 全量静态通读 + 隔离实例动态验证；(2) 安全专项子代理复审（含构造恶意 EPUB 在真实浏览器观测 CSP/沙箱、跨源 WS、DNS rebinding 前提验证）。两轮结论已交叉核验，**第二轮推翻了第一轮的两处判断**（见"第一轮的错误结论"）。

## 总览

- 类型检查 `npm run typecheck` 通过；`npm test` 12 用例全过；`dist/` 与 `src/` 行为一致（抽查无分叉）。
- 正向功能扎实：导入去重秒开、批注双写、MCP 8 工具、WS 往返、原子写状态，均有测试覆盖且实测正常。
- **核心问题**：服务对"本机任意网页都能访问 127.0.0.1"这一经典威胁面基本无防御——无认证、无 CORS/Origin 校验、无 Host 校验、无 CSRF 防护。多条跨源攻击链已实测成立，其中数条可被**任意恶意网页远程触发**，无需用户操作。
- 明确排除（已验证不成立）：任意文件**读**、命令注入、原型污染、ReDoS。

严重度：高＝恶意网页可远程触发，泄露隐私或破坏用户数据；中＝特定条件下功能错误或可被滥用；低＝健壮性/一致性瑕疵。

## 第一轮的错误结论（已纠正）

诚实记录，避免后续执行者沿用错误判断：

1. **"真实浏览器 CSRF 面仅限 multipart 导入端点"——错误。** 第一轮认为 JSON 端点因触发 preflight 而安全，忽略了**缺省值机制**：`clear-highlights` 在 body 为空时会退回 `state.get().book`（用户当前正在读的书）。攻击者用 `Content-Type: text/plain` + 空 body 发简单请求（无 preflight），`express.json` 不解析 → body 空 → 直接抹掉当前书。实测 `{"ok":true,"removed":1}`，批注与 notes.md 双双清空。见 H2。
2. **路径遍历评为"低危、实际可利用性低"——低估。** 第一轮只测了读（`GET /api/books/..` 返回 404），没测**写**。写这条链跨源可触发，实测把书籍文件写进库的父目录（默认 `~/Books/`），会覆盖同名文件。见 H3。

## 高危

### H1 · 跨站 WebSocket 劫持（CSWSH）+ AI 提示注入通道
- 位置：`src/server.ts:54-73`，upgrade 与 connection 均不校验 `Origin`。
- 实测：伪造 `Origin: https://evil.example.com` 握手**被接受**；立即收到 `hello`，含完整书库列表（书名/作者/章节标题/ID）与当前阅读状态——`visibleTextHead`（用户此刻正在读的原文）、章节、进度、CFI、选区。再发 `state:update` **成功篡改**服务器状态。
- 为什么现实可行：WebSocket 握手不受同源策略限制，任何网页都能 `new WebSocket('ws://127.0.0.1:4123/ws')`，默认端口可预测。
- **额外的产品级危害**：`.claude/skills/bookd/SKILL.md` 指示 AI 把 `selection`/`visibleTextHead` 当作"用户正在读/选中的内容"并据此作答。跨源可写这两个字段，等于**本机任一恶意网页可把任意文本塞进 AI 认为的"用户阅读上下文"**——这是一条对 AI 助手的间接提示注入通道，危害超出单纯的状态篡改。
- 修复：upgrade 阶段校验 `Origin`——不存在（MCP/curl 不带 Origin）或指向 `localhost`/`127.0.0.1`/`[::1]` 才放行，其余 `socket.destroy()`。

### H2 · 无预检 CSRF 抹掉当前书全部批注
- 位置：`src/server.ts:199-205` → `src/storage.ts:281-289`。
- 实测：`POST /api/commands/clear-highlights`，`Content-Type: text/plain`、空 body、伪造 Origin → 返回 `{"ok":true,"removed":1}`，`annotations.json` 清空、`notes.md` 中笔记消失。
- 机制：`text/plain` 属 CORS 简单请求，浏览器**不发 preflight**；`express.json` 不解析该类型 → `req.body` 为空 → `bookId` 退回 `state.get().book`（当前正在读的书）。攻击者一行 `fetch()` 即可销毁用户正在读的书的全部划线与笔记，且**不需要知道任何 ID**。
- 数据不可恢复（`notes.md` 被整体重写）。这是本次危害最直接的一条。
- 修复：变更类端点要求 same-origin 校验或自定义头（强制 preflight）；`clear-highlights` 不应在无显式 `bookId` 时静默作用于当前书。

### H3 · 跨源可触发的越目录写
- 位置：`src/storage.ts:66` ID 正则 `/^[\p{L}\p{N}._-]+$/u` 允许纯点段；`storage.ts:79-83` 用 `path.basename(fileName, ext)` 作书名。
- 实测链：上传文件名 `...md`（内容无一级标题，避免书名被首个标题覆盖）→ `basename('...md','.md')` = `..` → `safeName('..')` = `..` → 通过 ID 校验 → `path.join(root,'..')` 逃逸。返回 `{"id":"..","title":".."}`，`meta.json`/`source.md`/`notes.md`/`annotations.json`/`chapters.json`/`extracted/` 全部写进**库目录的父目录**（默认布局即 `~/Books/`）。
- 该导入端点是 multipart（无 preflight），伪造 Origin 实测 201 通过，故**恶意网页可远程触发**。同名文件会被覆盖。
- 同源问题的另一入口：EPUB 的 `<dc:title>..</dc:title>` 或 markdown 首个 `# ..` 标题也能得到 `id=".."`。
- 边界：`/` 被正则拒（`a/b`、`%2f` 均被拒），故**仅能上跳一级**，文件名固定，够不上任意文件写。
- 修复：ID 正则排除纯点段；`bookDir()` 结果 `path.resolve` 后断言落在 `root` 内。

### H4 · 无 Host 校验 → DNS rebinding 可绕过全部残余防护
- 位置：所有路由，无 Host allowlist。实测 `Host: bookd.evil.example` 照常返回 200。
- 危害：攻击者把自己域名重绑到 `127.0.0.1` 后即取得**同源**权限——可读 `/api/books/:id/chapters/*`（全书正文）、任意写高亮/导入/状态，且**响应可读**。这绕过了 H2/H3 之外那些"靠 preflight 挡住"的端点（`/api/open`、`goto`、`highlight`、`PUT /api/state`）。
- 这是通往全量读写的总闸，性价比最高的一道修复。
- 修复：全局中间件校验 `Host` 头在 `127.0.0.1:PORT`/`localhost:PORT` allowlist 内，否则 403。

## 中危

### M1 · multipart 导入 CSRF
- 位置：`src/server.ts:97-116`。实测伪造 Origin 上传返回 201，书进书库，并 `issueCommand({type:'open'})` **强制把用户阅读器切到攻击者的书**。与 H3 是同一入口的不同利用面。

### M2 · 逻辑章节按标题字符串匹配 → 章节索引错乱
- 位置：`src/client/FoliateReader.tsx:100` `findIndex(c => c.title === detail.tocItem?.label)`。
- 书内重复标题（中文书"练习""小结""第一节"常跨部重复）时恒命中第一个。实测构造：读到第二个"练习"时索引错误指向第一个 → 目录高亮错章、上报 `chapterIndex` 错误、章节态恢复错乱。直接影响"AI 感知位置"的准确性，是产品核心功能缺陷。
- 修复：用 section index → 逻辑章映射，或按唯一 href/cfi 匹配，不要用 title 反查。

### M3 · 文件桥 `.reading/state.json` 绑定启动 cwd，与方案语义矛盾
- 位置：`src/config.ts:23`。实测真实服务写死在 `bookd/.reading/state.json`（启动目录）。
- 方案第 5 节定义 ④ 为"任意 agent 读文件（兜底桥）"，本意每项目一份；单进程单 cwd 只写一处，其他项目的 agent 读不到。走 MCP 不受影响，断的是方案设想的文件兜底路径。
- 修复：明确为单一全局位置（如 `~/Books/bookd/state.json`）并更正文档；或由 skill 在各项目内建桥。

### M4 · 命令 fire-and-forget，无 UI 时静默失败却回报成功
- 位置：`src/server.ts:48-51,162-177`。无 WS 客户端连接时 `goto`/`open_book` 广播给 0 个接收者被丢弃，但仍返回成功。AI 会误以为"已带你跳过去了"。（`highlight` 不受影响——先落盘再广播。）
- 修复：回报投递客户端数，或无客户端时明确返回"阅读器未打开"。

### M5 · clear-highlights 无存在性校验，可凭空建目录
- 位置：`src/storage.ts:281-289` 对任意 `bookId` 直接写文件，不检查书是否存在。实测 `bookId:"attacker-created-dir"` 在库中凭空创建目录并写入。配合 H3 可在父目录写 `notes.md`。

### M6 · zip 炸弹无防护
- 位置：`src/epub.ts:47-48` `new AdmZip(buffer)` + `readZipText` 整体 `getData()`，**无解压体积上限、无条目数上限**；multer 允许单文件 200MB × 200 个（`server.ts:40`）。高压缩比 zip 炸弹经无预检的导入端点即可远程触发内存耗尽。
- 修复：解压前校验单条目/总解压大小与条目数，epub 解析设超时。

### M7 · 电子书 iframe 沙箱与宿主同源，唯一屏障是注入的 meta-CSP
- 现状（实测有效）：构造含内联 `<script>`、`<img onerror>`、`<iframe srcdoc>` 多种 payload 的 EPUB 在真实浏览器加载，全部被拦（sanitizer 移除 + CSP `default-src 'none'` 阻断，srcdoc 子文档继承父 CSP）；`connect-src 'none'` + `img-src` 仅 blob/data 有效封堵外传。
- 结构性弱点：foliate-js 的 iframe 是 `sandbox="allow-same-origin allow-scripts"`（`node_modules/foliate-js/paginator.js:234`、`fixed-layout.js:87`，浏览器控制台明确告警可逃逸沙箱），书文档经 blob 与宿主页**同源**——一旦有任何脚本执行成功，即取得对 `127.0.0.1:4123` 全部 API 的同源权限。而唯一屏障是靠**正则在字符串上拼接注入**的 meta-CSP（`book-document.ts:22-29`），对畸形文档（无 `<head>`、SVG 根文档、多 `<head>`）的健壮性依赖浏览器容错。
- 修复方向（中期）：书内容用独立 origin/端口隔离，或去掉 `allow-same-origin`（需评估 foliate 兼容性）；CSP 改由 HTTP 响应头下发，不让 meta 独扛。

## 低危

- **L1 · 非法 bookId 返回 500 而非 400**（`storage.ts:66` 抛错 → `server.ts:216-219` 一律 500）。实测 `GET /api/books/a%2fb` → 500。
- **L2 · WS 广播不排除发送者**（`server.ts:43-46`）。当前客户端不回发故无循环，但语义上有回声；未来若 `onState` 触发上报会成风暴（第一轮测试脚本因自身回发产生 1.5MB 洪水，侧面印证）。
- **L3 · WS 未设 `maxPayload`**，配合 broadcast 有放大效应。状态写盘有 180ms 去抖，缓解磁盘 DoS，CPU 消耗仍在。
- **L4 · 状态双命名**：文件桥 snake_case（`state.ts:6-21`）vs MCP/HTTP camelCase。不违反方案（方案只规定了文件桥），但对同时用两条通道的 agent 是认知负担，建议 README 说明。
- **L5 · `notes.md` 内容注入**：`storage.ts:39-49,277` 把 `text`/`note` 原样写入，可注入 Markdown/伪造章节标题，用户用其他工具打开时可能被渲染。
- **L6 · `BOOKD_HOST` 可绑 `0.0.0.0`**（`config.ts:20`，默认 `127.0.0.1` 安全）。因零认证，一旦绑非回环地址即把整库暴露给局域网。建议文档强警告或禁止非回环绑定。
- **L7 · `.claude/settings.local.json` 设 `enableAllProjectMcpServers: true`**：自动信任本项目所有项目级 MCP，配置面的轻微风险点。
- **L8 · Markdown 侧安全依赖库默认值**：`MarkdownReader.tsx:197` 用 `react-markdown` 且未引入 `rehype-raw`，原始 HTML 不渲染，`javascript:` 靠默认 `urlTransform` 过滤。当前安全，建议显式固化。

## 已验证不成立（排除项）

- **任意文件读**：点名验证的"恶意网页导入 `~/.ssh/id_rsa` 再经章节 API 读出"**不成立**。导入用 multer `memoryStorage`，只处理上传 buffer，`fileName` 仅用于取扩展名/标题，从不作读取路径。CLI `bookd import <path>` 虽按本机路径读，但是本地用户主动操作，远程不可达。
- **命令注入**：唯一子进程 `cli.ts:49` 用数组参数、无 shell、无用户输入拼接。
- **原型污染**：`state.ts:54-80` 虽有展开合并，但 `normalise` 用显式字段重建纯字面量对象；其余按字段显式构造，无深合并。
- **ReDoS**：无 `new RegExp(用户输入)`，各正则线性或惰性，无灾难性回溯。
- **dist/src 分叉**：抽查 ID 正则、multer/upgrade、sanitizer 与 CSP 字符串均一致。

## 设计符合性对照

符合：
- ✓ 生命周期分离（常驻 bookd 持状态 + 无状态 MCP stdio 薄客户端）——方案"不可妥协点"，实现正确，有真实 stdio 子进程测试佐证。
- ✓ MCP 8 工具齐备（旧记忆记的"7 个"已过时）。
- ✓ 渲染零 AI 参与；书库目录结构；批注双写；文件桥 snake_case schema；epub/mobi/azw3/markdown + foliate-js；DRM 不支持；PDF 可插拔且延后。

偏差：
- ⚠ 文件桥"任意 agent 读文件兜底"语义被 cwd 绑定削弱（M3）。
- ⚠ 方案第 12 节风险清单未覆盖本地常驻服务的 Origin/CSRF/CSWSH/DNS-rebinding 面。这是"常驻 HTTP+WS + 侧栏 + 任意浏览器可访问"形态的固有风险，应补入方案并落实防护。

## 值得肯定

- 状态持久化稳健：临时文件 + rename 原子写、180ms 去抖、pendingWrite 串行链、规范化 clamp/slice。
- 电子书 XSS 防御**实测有效**（sanitizer + CSP 双层，多种 payload 均未执行，外传被封堵）——结构可改进，但当前有效。
- 导入去重（sourceHash）实现同书秒开命中缓存。
- 测试质量高：覆盖真实 stdio MCP 子进程、WS 往返、批注双写、MOBI 元数据补齐、markdown 拆章。
- 类型严格，typecheck 干净；中文排版品味迁移到位。

## 建议修复优先级

1. **H4 Host 白名单**——挡 DNS rebinding，堵住通往全量读写的总闸，性价比最高。
2. **H1 WS Origin 校验**——堵跨源数据泄露 + AI 提示注入通道。
3. **H2 变更类端点 CSRF 防护**——尤其 `clear-highlights`（数据不可恢复）与 `import`。
4. **H3 + M5 收紧 bookId 校验**——排除纯点段，`path.resolve` 后断言在库内，写前校验书存在。
5. **M2 章节索引**——影响核心感知准确性。
6. M4 命令回执如实化 → M6 zip 上限 → M3 文件桥语义（先文档消歧义）→ L 类按需。
7. 中期：M7 书内容 origin 隔离。
